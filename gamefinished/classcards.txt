Legend:
  +           public
  -           private
  ~           package (no access modifier written in the code)
  c           constructor
  {static}    static attribute / method (underlined in a UML diagram)
  {final}     final attribute (cannot be changed after it is set)
  {abstract}  abstract class (there are no objects of this class itself)

Attributes:  visibility name: type
Methods:     visibility name(parameters): return type

============================================================
RELATIONS BETWEEN THE CLASSES
============================================================

Multiplicities are written like this:
  ClassA [how many ClassA] —— [how many ClassB] ClassB

------------------------------------------------------------
1. Inheritance (Vererbung)   ClassA ——▷ ClassB
------------------------------------------------------------
 - Book    ——▷ Item
 - Potion  ——▷ Item
 - Number  ——▷ Item
 - Key     ——▷ Item
   Book, Potion, Number and Key inherit name, subject, description and rarity
   (and their getters/setters) from Item. Item is abstract.
   Weapon does NOT inherit from Item.

------------------------------------------------------------
2. Composition (Komposition)   ClassA ◆—— ClassB
------------------------------------------------------------
 - Adventure [1] ◆—— [0..1] Character      (attribute: player)
   Adventure creates the player in start(). Before start() player is null, so 0..1.
   The player cannot exist without the game.

 - Character [1] ◆—— [1] Inventory         (static attribute: inventory)
   The inventory is created inside the Character class and only exists with it.
   Because it is static, it belongs to the class Character, not to one Character object.

------------------------------------------------------------
3. Aggregation (Aggregation)   ClassA ◇—— ClassB
------------------------------------------------------------
 - Inventory [0..1] ◇—— [0..*] Weapon      (attribute: weaponSlots)
 - Inventory [0..1] ◇—— [0..*] Key         (attribute: keySlots)
 - Inventory [0..1] ◇—— [0..*] Book        (attribute: bookSlots)
 - Inventory [0..1] ◇—— [0..*] Potion      (attribute: potionSlots)
 - Inventory [0..1] ◇—— [0..*] Number      (attribute: numberSlots)
   The weapons and items also exist without the inventory (as static objects in
   their own classes). The inventory only collects them, so it is an aggregation.

------------------------------------------------------------
4. Association (Assoziation)   ClassA ——> ClassB
------------------------------------------------------------
All associations are directed: only the class on the left knows the class on the right.

 - Room      [1..*] ——> [1]    Floor       (attribute: floor)
 - Room      [0..*] ——> [1]    Subject     (attribute: subject)
 - Item      [0..*] ——> [1]    Subject     (attribute: subject)
 - Weapon    [0..*] ——> [1]    Subject     (attribute: subject)
 - Boss      [0..*] ——> [1]    Subject     (attribute: subject)
 - Character [0..*] ——> [1]    Subject     (attribute: subject)
 - Character [0..*] ——> [0..1] Boss        (attribute: inFightWith, only set during a fight)
 - Character [0..*] ——> [0..1] Room        (attribute: currentRoom, null when you are in the hallway)
 - Character [0..*] ——> [1]    Floor       (attribute: currentFloor)
 - Adventure [0..*] ——> [0..1] Subject     (attribute: tempCharacterSubject, only used in start())
 - Subject   [1]    ——> [1]    Subject     (attribute: strongAgainst, reflexive association)
 - Subject   [1]    ——> [1]    Subject     (attribute: weakAgainst, reflexive association)
   The strongAgainst/weakAgainst links are set in a static block at the end of Subject.

Additional notes
------------------------------------------------------------
Static objects of the own class:
   Most classes keep their game objects as static attributes of their own type:
   Room 57, Weapon 55, Key 21, Potion 8, Subject 6, Boss 6, Book 6, Number 5, Floor 4.
   In the UML diagram these are static attributes (underlined), not extra relation lines.

Dependencies (benutzt-Beziehung, dashed arrow - - ->), not one of the four relations above,
because there is no attribute. The class only uses the other class inside its methods:
 - Adventure - - -> Loot, Room, Floor, Boss, Weapon, Key, Inventory
 - Character - - -> Weapon, Item, Book, Potion, Number, Key, Adventure (Adventure.scanner)
 - Loot      - - -> Room, Weapon, Key, Item, Potion, Book, Number, Subject, Character (inventory, readDecision)
 - Inventory - - -> Item (parameters of addItem, removeItem, printItems)
 - Weapon    - - -> Character (parameter of calcDamage)
 - Boss      - - -> Character (parameter of calculateBossDamage)

Java library classes that are used (normally not drawn in the diagram):
   Scanner (Adventure), Random (Adventure, Loot, Weapon), ArrayList / List (Adventure, Inventory, Loot, Character)
